## 一、本地 / 在线数据源解耦

**症状**：清空本地成绩后，侧栏仍显示一个 Rating，但推荐页整页为空。用户原话「本地和在线似乎共用一个存储空间」。

**根因**：`dfPlayerName` / `dfRating` 被**四条路径**写入（在线查分 + 水鱼 Token 导入 + 水鱼 OAuth 导入 + 落雪导入），而 `dfBest35/15` **只有在线查分**才会填。于是清空本地后，侧栏挂着一个没有 B50 明细的孤儿数字，推荐引擎因缺明细返回 null。

**方案**：按来源拆成两套互不干扰的状态。

| 来源 | 字段 | 生命周期 |
|---|---|---|
| 本地 | `localB50` / `importedPlayerName` / `importedRating` | 清空本地成绩时一并清除 |
| 在线 | `onlinePlayerName` / `onlineRating` / `onlineBest35` / `onlineBest15` / `loading` / `error` | 仅「在线查分 / 清除查分」影响 |

推荐引擎改为「有 B50 明细就用在线，否则退回本地 B50」，不再依赖「有没有名字」这种间接信号。旧 `df*` 字段直接删除、不留别名（`tsc` 兜住漏改）。

**保留的旧行为**：导入时会清空在线查分结果。原代码导入时本就把 `dfBest35/15` 写空，若只停止写入而不清空，「查了别人的 B50 再导入自己成绩」会让推荐串号。

## 二、检索与筛选

### 2.1 定数按需显示

第一轮把定数常显在难度徽章旁，每首歌最多 5 个难度 → 一行最多 10 个元素，密度过高。

改为按需：只有使用「定数区间 / 等级标签 / 拟合口径」筛选时才补上定数；仅勾难度时不显示（徽章本身已表达难度）。规则抽成 `shouldShowLevelValue()`。

### 2.2 官标与拟合定数双轨（行为变更）

**旧语义**：勾选「按拟合定数筛选」后，等级与定数范围会**一起切换**成比拟合值。两个维度被捆成一套，表达不了「官标 13+ 的大类里再筛拟合 < 13.6」。

**新语义**：

- 官标：等级 / 最低-最高定数 —— **永远**按官标比，不再被拟合口径劫持
- 拟合：勾选口径后出现独立的「拟合定数区间」，与官标条件自由叠加

`AdvancedFilters` 新增 `fitLevelValueMin` / `fitLevelValueMax`；`levelValueMin/Max` 与 `level` 回归纯官标语义。原先用于把等级标签换算成拟合区间的 `levelLabelTenths()` 随之删除。

两组区间都遵循「填反不生效 + 标红提示，不替用户改值」。

## 三、别名搜索：两处互相独立的失效

### 3.1 生产环境没有代理

`fetch('/alias-api/maimaidx/maimaidxalias')` 依赖 `vite.config.ts` 的 `server.proxy`，而 `server` **只对开发服务器生效**。生产是 GitHub Pages，且以 `/` 开头的 fetch **不受 `base: '/MaiBuddy/'` 影响**，实际请求打到 `https://rgxiaoze.github.io/alias-api/...` → 404 → 别名索引永远为 null → 所有别名搜索 0 结果。

改为按环境分流：dev 走代理，生产直连社区接口。

### 3.2 别名到货后结果不刷新

筛选结果用 `useMemo` 缓存，依赖里有 `statsEpoch` 这类显式版本号，却没有别名加载状态。首次搜索若早于别名到货，空结果会被一直缓存；而加载本身成功，所以失败提示也不出现。

新增 `useAliasVersion()`（`useSyncExternalStore`），别名到货即 bump 版本号，检索页与统计页把它放进筛选依赖。

### 3.3 附带加固

- `parseAliasEntries()`：兼容 `{code, content}` 与裸数组，`Alias` 缺失归一为 `[]`。此前**一条脏数据会让整份索引构建抛错**，全体别名一起失效
- 加载失败时检索页显示提示（`getAliasLoadError()` 此前导出了却全项目 0 处调用，失败完全静默）
- 开发环境输出载入摘要，并在 `window` 挂 `__aliasDebug(query)`，用于区分「索引没加载」与「ID 对不上」

## 四、实装年校正静默失效

**症状**：新曲详情页的「拟合定数」没有下拉箭头。

**根因**：箭头只在「校正真的改变了数值」时出现，而校正量依赖 `install-year.json.gz` 里的实装年。该文件是 4803 条的一次性产物、**仓库里没有生成脚本**，新曲入池后必然缺条目 → `getInstallYear` 返回 null → 校正量 0 → 数值等于水鱼原始值 → 箭头不出现。用户看到的是「没有箭头」，实际是「没校正」。

**方案**：

- 新增 `inferInstallYearFromVersion()`：旧框曲（version ≤ 700）不推断，DX 时代按 `JP_TO_CN_YEAR` 由版本号推断国服年份
- `statsService.setSongYearMap()` 注入兜底映射；**精确数据优先**，缺失时才用推断值
- 新增 `installYearInferred` 标记，详情页展开区区分「实装校正」与「推断实装年校正」
- 两者都没有时显示「实装年未知，未校正」，让缺口可见
- 统计已构建、兜底映射晚到时，`loadStats` 重建一次

## 五、删掉的：推荐卡「该档均」

它与左侧的预测成绩口径不同——该档均是算术平均、窗口 ±0.05~±0.25，预测成绩是中位数、窗口 ±0.3。并排显示会出现「你的档均 96.4%，但预测你能打 96.6%」这种自相矛盾的观感，tooltip 写的「0.1 精度」也和实现不符。

按维护者决定直接移除；`difficultyTier.ts` 的 `averageAtLevel()` 与其测试保留（独立工具函数，将来若以别的形式回归可直接复用）。

## 六、踩坑记录

1. **以 `/` 开头的 fetch 既不走 `base`，也不走 `server.proxy`** —— 开发能跑、线上 404 的典型来源。以后涉及跨域接口，必须按环境分流并写清注释。
2. **静默失败最贵**。别名加载失败无提示、实装年缺失无提示，两次都是「看起来功能坏了但没人知道为什么」。凡是「数据缺失会导致功能降级」的地方，都要有可见信号。
3. **一次性产物 = 定时炸弹**。`install-year.json.gz` 没有生成脚本，新曲一进池就开始失效。这类数据要么有生成脚本、要么明确标注适用范围。
4. **统计量口径混用会产生「自相矛盾」**。同一批数据用平均值和中位数并列展示，用户会认为是 bug。
5. **`git switch -c 新分支 origin/main` 会把上游设成 `origin/main`**，此时裸 `git push` 会直接推 main。建完分支要立刻确认上游，首次推送显式 `-u`。
