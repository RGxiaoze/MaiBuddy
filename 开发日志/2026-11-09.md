## 发现并修复的问题

### 1. 钻取链接直接访问显示 0 首（严重）

`SongList` 从不在挂载时加载成绩，只有导入后才加载。直接刷新或分享 `?rate=` 链接时 `scores` 为空，筛选匹配不到任何曲目。

根因更深：曲库 / 成绩 / localB50 的加载分散在各页面，谁先打开谁负责，导致：
- 推荐页直接打开显示「暂无成绩数据」
- 曲目页侧边栏显示「请登录」

**修复**：统一到 [MainLayout.tsx](src/components/layout/MainLayout.tsx) 初始化（songs + scores + computeLocalB50），各页面仍可幂等调用。

### 2. 难度钻取口径与统计卡不一致（中等）

`playedFilter` 只判断「该曲目任意难度有匹配成绩」，忽略 `?lv=`。导致统计卡显示 1241，点进去列表 1318。

**修复**：[SongList.tsx](src/pages/SongList.tsx) 中成绩筛选叠加难度时，按「成绩所属难度」匹配（`sc.levelIndex === drillLevel`）。

### 3. FC/FS 显示 `undefined`（中等）

`fsType` 存在 `"sync"` 取值（2778 条中 1112 条），但 `FS_LABELS` 没有该键，卡片渲染成「FC undefined」，曲目详情页同样受影响。

**修复**：[constants.ts](src/data/constants.ts) 补 `sync: 'SYNC'`。

### 4. 移动端达成率被截断（轻微）

375px 三列卡片可用宽度约 45px，`100.5104%` 截断成 `100.5…`。

**修复**：[B50TileCard.tsx](src/components/shared/B50TileCard.tsx) 移动端降到 2 位小数 + 10px 字号，桌面保留 4 位。

# 后续：批次 5 — SSS 口径拟合定数

## 起因

用户指出「SSS 与 SSS+ 甚至 AP 的难度并不对等」，怀疑单一 fit_diff 不够用。

## 过程中的一次自我纠正

我先做了单调性检验，发现 84.4% 的谱面 `dist[13] > dist[12]`，据此判断「项目把 SSS/SSS+ 标反了」。

**这个判断是错的。** 从 Diving-Fish 前端源码找到了权威定义：

```js
const e = ["D","C","B","BB","BBB","A","AA","AAA","S","S+","SS","SS+","SSS","SSS+"]
const i = ["Not FC","FC","FC+","AP","AP+"]
dist[i] ↔ e[i]
```

索引本身正确。我的错误在于假设「SSS+ 是 SSS 的子集」——实际上两者是**互斥区间**
（SSS = 100.0~100.4999，SSS+ = ≥100.5）。所以「SSS+ 人数更多」完全正常。

教训：在确认档位定义前不要下「数据有 bug」的结论。

## 真正的发现

| 指标对 | 相关系数 |
|--------|----------|
| SSS 率 ↔ SSS+ 率 | **0.35** |
| fit_diff ↔ SSS 率 | -0.16 |
| fit_diff ↔ SSS+ 率 | -0.81 |

现有 fit_diff 几乎完全由 SSS+ 率驱动，**不反映 SSS 难度**。

关键修正：不能用「SSS 单独率」（100~100.5 的窄区间）作信号，要改用
**累计 SSS 及以上率**（`dist[12] + dist[13]`）——相关性从 -0.16 提升到 -0.76。

## 算法与局限

全量 5561 个样本谱面回归，斜率 **-1.132**，R² 0.376。

分段方向一致率：

| 定数区间 | 样本 | 与 fit_diff 方向一致 |
|---------|------|---------------------|
| < 10 | 2963 | 56.2% |
| 10–12 | 819 | 73.0% |
| **12–13.9** | 1474 | **78.1%** |
| ≥ 14 | 305 | 73.1% |

低定数段不可用：SSS 率接近饱和（部分谱面 60%~90% 玩家都能 SSS），无区分度。
因此 **只在官方定数 ≥ 12 时展示**。

## 实施

- `statsService` 新增 `cumSssRate` 字段（ChartStatSummary / FitDiffAvg）
- 新增 `SSS_FIT_SLOPE` / `SSS_FIT_MIN_LEVEL` 常量与 `computeSssFitDiff()`
- 曲目详情底部展示两行：`拟合定数（SSS+）` 与 `拟合定数（SSS）`
- 差值补上负号（原先负数只靠颜色区分，两行并列时易误读）
- 新增 6 项单元测试

实测：Glorious Crown MASTER 14.8 → SSS+ 14.63 / SSS 14.73；
BASIC 7.0 只显示 SSS+ 行（7.19），符合预期。

## 遗留

- 斜率 -1.132 是全量统一值，未按定数区间分段标定（分段会过拟合，暂不做）
- 15 级谱面样本过少（305），数值参考价值有限，用户已表示不关注

### 算法细节

| 决策 | 理由 |
|------|------|
| 票数门槛 30 | 实测覆盖 1265/1294 首；`Technicians High` 5 票 80% 不能霸榜 |

## 起因

## 实测发现的三处对接错误

curl 逐端点核对，发现此前「落雪已支持 CORS」的结论只对了一半：

| 检查 | 结果 |
|------|------|
| `POST /oauth/token`（原默认路径） | **405** —— 端点错了 |
| `POST /api/v0/oauth/token` | 401 `invalid_client` + 完整 CORS ← 真实端点 |
| `POST /oauth/revoke` | **405** —— 同样错了 |
| `POST /api/v0/oauth/revoke` | 401（端点存在）← 正确路径 |
| `GET /api/v0/maimai/player/{friend_code}/scores` | 401 无鉴权 —— **好友码匿名查询不可行** |
| 官方 `Score` 结构体曲目 ID 字段 | 是 **`id`**，不是 `song_id` —— 原判断会把所有成绩静默丢弃 |

`id` 那条最隐蔽：`toDfScores` 里 `typeof raw.song_id !== 'number'` 直接 `continue`，
真实数据会**一条不剩**，而且报错信息是「该账号没有成绩数据」，把人往错方向引。

## 实现

- `oauthCore` 新增可选 `revokePath`（默认值不变，水鱼零影响）
- `lxnsOAuth` 补 `tokenPath: '/api/v0/oauth/token'`、`revokePath: '/api/v0/oauth/revoke'`，填入应用 ID
- `toDfScores` 兼容 `id` / `song_id`（同时存在以 `song_id` 为准），`LxnsScore` 两字段都可选
- `playerStore.importScoresViaLxns()`：拉成绩 → 曲库补定数 → `bulkImportScores` → 昵称/Rating 取 `fetchMyPlayer`
- `OAuthCallbackHandler` 从硬编码水鱼改为按 `readPendingProviderId()` 分派两家
- 导入弹窗新增「落雪」卡片：授权按钮（未配置时降级为文字提示）+ 折叠的「个人 API 密钥导入」+ 已授权时「退出授权」
- `UserInfoCard` 菜单新增「退出落雪授权」

密钥输入**不落盘**（与水鱼 Import-Token 的「记住」不同）：落雪导入是一次性动作，
成绩进 IndexedDB 后不再需要密钥，少存一个秘密。

## 成绩导入/导出支持落雪 CSV（同日，用户提供导出文件）

用户提供了一份落雪导出的 `maimai-scores.csv`（2827 条），要求按该格式改造导入/导出。

### 格式差异

| 项 | 本站 JSON 备份 | 落雪 CSV |
|----|----------------|----------|
| 结构 | `{ version, count, scores: [...] }` | 平面表格，13 列 |
| 曲目 ID | `songId`（DX = 基础 + 10000） | `id` 基础 ID，标准/DX 共用 |
| 区分谱面 | `songType` | `song_type` |
| 达成率 | `achievements` | `achievements` |
| 定数 | `levelValue` 自带 | **不含**，需曲库补齐 |
| DX Rating | 整数 | 8 位小数浮点（如 `310.86037512`） |

曲名含逗号与双引号（`"Endless, Sleepless Night"`、`"Little ""Sister"" Bitch"`），
**不能用 `split(',')`**，按 RFC 4180 解析。

### 实现

- 新增 `utils/lxnsCsv.ts`：`parseCsv`（引号包裹 / `""` 转义 / CRLF / BOM）、
  `parseLxnsScores`（表头校验 + 关键字段缺失则跳过行）、`buildLxnsCsv`
- `importScoresFromFile(file, songMap?)` 按首个非空白字符分派：`{` 走 JSON，其余走 CSV
- CSV 导入复用在线导入的 `toDfScores`：DX 换算、定数补齐、曲库缺失丢弃，口径完全一致
- `dx_rating` 取 `Math.floor`，避免浮点进入整数评分口径
- `play_time` 回填到 `playDate`；导出时无时间信息则补 `00:00:00`
- `exportScoresAsLxnsCsv()`：列与落雪完全一致，DX 取余回基础 ID，可回流到落雪
- 导入弹窗 `accept` 改为 `.json,.csv`，文案与按钮同步调整
- 用户菜单新增「导出落雪 CSV」，JSON 备份保留

## Rating 总分出现小数（同日，用户反馈）

用户指出：舞萌 Rating 是**整数相加**，总分不该有小数，应为 `16230`。

### 根因

落雪 API 的 `dx_rating` 是 8 位小数浮点（`310.86037512`），而本项目 `DfScore.dxRating`
直接透传，导入时未取整。CSV 导入路径我做了 `Math.floor`，但 **OAuth / 密钥导入路径漏了**，
两条路径口径不一致 —— 同一份数据走不同入口，总分一个带小数一个不带。

`computeRating()` 本身是 `Math.floor`，所以只有「信任上游评分」这条分支会漏。

### 修复

两处都取整，分别对应「新数据」与「已存的历史数据」：

1. `toDfScores`：`dxRating: Math.floor(raw.dx_rating ?? 0)` —— 堵住源头
2. `computeB50`：`Math.floor(s.dxRating)` —— 读取时取整，已导入的浮点数据无需重导即修复

顺带删掉 CSV 导入里重复的取整（源头已取整）。

新增 2 项测试：落雪浮点评分转整数、存储值带小数时总分仍为整数。

## 搜索筛选 / 宴会场 / 推分数量 / 探索复健（同日）

### 1. 等级筛选只有 13–15

根因：`LEVEL_PRESETS` 硬编码 5 档，且走的是**定数区间**而非官标等级。

改为从曲库动态生成全档位下拉（1…15+），直接写 `level` 字符串；
「最低/最高定数」保留做精确数值。语义现在清晰：**等级管档位，定数管数值**。

顺带剔除 `12+?` 这类「定数未确认」的标签 —— 它们不是可用档位，需要精确查找时走定数或搜索。

### 2. 宴会场（ID ≥ 100000）混在主列表

宴谱没有定数与难度数据、等级显示 `?`，参与排序和筛选没有意义。

改为默认隐藏，筛选区加「显示宴会场」开关（`AdvancedFilters.includeUtage`）。
实测：默认 1343 首，勾选后 1405 首。

### 3. 推分建议数量

`MAX_SUGGESTIONS_PER_POOL = 30` 拆成 `MAX_B15_SUGGESTIONS = 15` / `MAX_B35_SUGGESTIONS = 35`；
`PushGroup` 新增 `defaultVisible`，B15 默认展开 5 条、B35 默认 10 条，其余收在「展开全部 N 条」里。
排序不变（容易在前），所以默认看到的就是最容易那几条。

### 4. 探索：三个月没玩的谱面

**数据前提**（关键）：水鱼 API 不含任何时间戳，导入后 `playDate` 全是导入当天；
只有落雪提供 `play_time`。硬用会导致「所有谱面都显示今天玩过」，推荐彻底失效。

- 补齐链路：`LxnsScore.play_time` → `DfScore.playDate` → `ScoreRecord.playDate`
  在线导入与 CSV 导入共用同一条路径（CSV 里重复的映射逻辑已删）
- `toInternalScore` 的 `playDate` 统一为日期精度（原先是完整 ISO 串）
- 探索新增 `staleKeys`：这些谱面仍属已游玩，但允许回到推荐池
- 可信度判定：成绩的 `playDate` 取值 ≤ 1 种 → 视为无时间数据，**不启用** stale 逻辑，
  保持原有「推荐没打过的谱面」行为；有真实时间数据时，超过 3 个月没碰的谱面才会回到池子
- 禁止降级推荐仍按**全部**已游玩记录判断，不受 stale 影响
